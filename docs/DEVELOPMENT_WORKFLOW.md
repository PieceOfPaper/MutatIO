# 개발 워크플로

- 마지막 갱신: 2026-10-17
- 목적: GPT 기획, 코딩 에이전트 구현, 사용자 직접 수정이 충돌하지 않도록 작업 방식을 통일

## 역할 구분

### GPT 기획 세션

- 게임 아이디어와 규칙을 구체화합니다.
- 확정 내용은 `GAME_DESIGN.md`, 미결정 내용은 `OPEN_DESIGN_QUESTIONS.md`에서 관리합니다.
- 중요한 결정과 번복은 `DECISIONS.md`에 기록합니다.
- 구현 상태를 추측하여 완료로 적지 않습니다.

### Codex와 Claude Code

- 저장소의 현재 코드와 문서를 읽고 구현합니다.
- 작업 전 로컬 변경을 확인하고 보존합니다.
- 미결정 사항을 임의로 장기 구조에 고정하지 않습니다.
- 구현이 문서의 규칙이나 실행법을 바꾸면 관련 문서를 함께 갱신합니다.
- 수행한 테스트와 수행하지 못한 검증을 구분해 보고합니다.

### 사용자 직접 작업

사용자의 로컬 변경은 언제든 발생할 수 있으며 가장 최신의 실제 작업일 수 있습니다. 에이전트는 이를 임의로 정리하거나 되돌리지 않습니다. 문서와 코드가 달라졌다면 차이를 먼저 설명하고 사용자가 의도한 변경인지 확인하거나 안전하게 문서에 반영합니다.

## 작업 흐름

```text
기획 논의
   ↓
확정·미결정 문서 분리
   ↓
작은 구현 단위 선택
   ↓
코드 및 테스트 작성
   ↓
Unity·WebGL에서 검증
   ↓
기획/기술/README 문서 동기화
   ↓
사용자가 변경 확인
   ↓
사용자 요청 시 커밋 (푸시는 주로 사용자가 직접)
```

## 브랜치와 커밋

에이전트는 사용자가 요청할 때만 커밋하고, 기본적으로 `main`에 바로 커밋합니다. 푸시는 사용자가 요청할 때만 합니다. 자세한 규칙은 `AGENTS.md`의 "커밋·브랜치·푸시"를 따릅니다.

사용자가 브랜치를 나누라고 요청하면 다음 이름을 사용합니다.

- 기능: `feat/<topic>`
- 수정: `fix/<topic>`
- 문서: `docs/<topic>`
- 실험: `experiment/<topic>`

커밋 메시지는 한국어로 작성합니다. 커밋은 한 가지 의도를 설명해야 하며 자동 생성 파일이나 관련 없는 포맷 변경을 섞지 않습니다.

## 기획 변경 처리

1. 현재 코드가 어떤 행동을 하는지 확인
2. 기존 기획과 달라진 부분 식별
3. 확정 변경이면 `GAME_DESIGN.md` 갱신
4. 결정 이유를 `DECISIONS.md`에 추가
5. 해결된 질문을 `OPEN_DESIGN_QUESTIONS.md`에서 정리
6. 실행이나 이해에 영향이 있으면 `README.md` 갱신

문서만 과거로 되돌려 코드와 억지로 맞추지 않습니다.

## 완료 기준

- 요청한 행동이 구현됨
- 관련 컴파일 오류가 없음
- 적절한 자동 테스트 또는 수동 검증을 수행함
- 기존 기능의 명백한 회귀가 없음
- WebGL 관련 기능은 필요한 브라우저 검증을 수행함
- 변경된 규칙과 사용법이 문서에 반영됨
- 남은 한계와 미검증 항목이 명시됨

## README 갱신 조건

Unity 버전, 필수 모듈, 시작 씬, 프로젝트를 여는 방법, CLI 연결법, 빌드·실행법, 주요 문서 경로, 프로젝트 상태나 지원 플랫폼이 바뀌면 README를 확인합니다. README는 계획과 구현 완료를 구분해 표현합니다.
