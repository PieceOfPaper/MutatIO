## 2026-10-17 — 클라이언트·서버 저장소 분리

- 상태: 승인
- 결정: 저장소 루트에 `Client/`(Unity 클라이언트 프로젝트)와 `Server/`(게임 서버 프로젝트) 폴더를 둡니다. 기존 Unity 프로젝트는 `Client/`로 옮기고, `Server/`는 서버 기술이 결정될 때까지 비워 둡니다.
- 이유: IO 게임은 클라이언트만으로 동작하지 않고 별도 서버가 필요하므로, 두 프로젝트의 경계를 저장소 구조에서부터 분리하기 위함입니다. 서버 기술 선택은 이 시점에 미결정이었으며, 아래 '서버 기술 스택' 결정으로 확정되었습니다.

## 2026-10-17 — 서버 기술 스택

- 상태: 승인
- 결정: 게임 서버는 ASP.NET Core(.NET 10 LTS)로 만들고, 클라이언트와는 WebSocket으로 통신합니다. 게임 규칙과 프로토콜 정의는 `Shared/`의 순수 C# 코드(netstandard2.1, C# 9)로 작성하여 Unity(로컬 UPM 패키지)와 서버(프로젝트 참조)가 함께 사용합니다.
- 이유: Unity WebGL 클라이언트는 브라우저 제약으로 UDP를 쓸 수 없어 WebSocket이 사실상 유일한 전송 방식입니다. 서버를 C#으로 만들면 게임 규칙 코드를 클라이언트와 공유할 수 있고, 2D IO 게임 규모에서는 Unity 헤드리스 서버보다 가볍게 많은 인원을 처리할 수 있습니다.
- 검토한 대안: Unity 헤드리스 서버 + Netcode for GameObjects·Mirror·FishNet(서버가 무겁고 프레임워크 결합이 큼), MagicOnion(브라우저에서 브리지가 필요하고 RPC 중심), SignalR(WebGL 클라이언트 지원이 애매함), Colyseus·Nakama(C# 코드 공유 불가).
- 아직 정하지 않은 것: 직렬화 라이브러리(MemoryPack 또는 MessagePack-CSharp 후보), Unity WebGL용 WebSocket 클라이언트 구현, 서버 틱, 권위 범위, 방 구조, 호스팅.
- 후속: Unity WebGL용 WebSocket 클라이언트는 jslib 브리지(`WebGLWebSocketTransport`)로 구현했습니다. 세부는 [기술 방향](TECHNICAL_DIRECTION.md)에 있습니다.

## 2026-10-17 — 플레이 흐름과 접촉 규칙 구체화

- 상태: 승인
- 결정: 캐릭터 외형 선택·닉네임 입력·조작 선택 후 작은 초식 생명체로 입장합니다. 사망 후 결과를 보고 확인 버튼으로 첫 화면에 돌아갑니다.
- 결정: 방향 입력형(키보드/가상 조이스틱)과 포인터 입력형(마우스/터치 위치 이동)을 제공합니다. 세부 입력 동작은 미결정입니다.
- 결정: 캐릭터는 원형을 기본으로 하며 초식·육식은 색, 캐릭터 종류는 형태 위주로 구분합니다.
- 결정: 좌측 상단 랭킹, 우측 상단 설정, 머리 위 닉네임과 남은 포만 게이지를 표시합니다.
- 결정: 근처 먹이는 자석처럼 당겨져 자동 섭취됩니다. 초식 먹이는 초록색, 육식 먹이는 붉은색입니다.
- 결정: 큰 육식이 작은 초식 또는 작은 육식과 접촉하면 작은 개체가 죽습니다. 초식끼리의 접촉은 사망을 일으키지 않습니다.
- 결정: 성장에 따라 카메라 표시 영역을 넓힙니다. 스페이스/모바일 버튼으로 쿨타임이 있는 대시를 사용합니다.
- 근거: 2026-10-17 사용자 플레이 구상. 구체적인 수치와 동일 크기 접촉 등 미정 조건은 OPEN_DESIGN_QUESTIONS에 유지합니다.

## 2026-10-17 — 사망 드롭 조건 변경

- 상태: 승인 — 이 항목이 같은 날짜의 기존 '핵심 자원 순환' 및 '점수와 몸집' 항목 중 모든 개체의 사망 드롭을 대체합니다.

- 변경: **초식 생명체 사망 시에만** 이번 생의 누적 섭취량에 비례한 육식 먹이를 생성합니다. 육식 사망은 고기를 생성하지 않습니다.

- 영향: 육식끼리 처치할 수 있으나 그 사망으로 먹이가 생기지 않습니다. 식량 순환과 포식자 개체 수 변화를 테스트합니다.
